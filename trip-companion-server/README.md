# 出行伴侣 Trip Companion

**一句话：以「行程」为中心的多人出行协作后端。**

三五个朋友约好出去玩，一趟出行要操心的事其实很碎：谁收拾了什么（清单）、
钱谁垫的怎么分（AA）、几点发车（车票提醒）、明天要不要带伞（天气）、
去哪吃去哪玩（推荐）。这个项目把这些收进**同一个行程**，几个人共用一份、随时同步。

> **技术栈**：Java 21 · Spring Boot 3.3 · Spring Data JPA · MySQL 8 / H2 · Maven
> **状态**：已部署上线（Windows 本机服务器，登录自启）· 可现场演示
> **规模**：13 个包 · 37 个 REST 接口 · 9 张表 · 76 个 Java 文件 · 约 8600 行
> **质量**：106 个单元测试 · 8 套端到端验收脚本（323 项检查，全量回归）

---

## 一、这是什么（30 秒版）

一个**多人出行协作工具的后端**：所有数据挂在「行程」下，几个人共同维护同一份。

它替代的东西：微信群接龙 + 备忘录清单 + 计算器分账 —— 全部收进一个行程。

和"后台管理系统"式的学生项目的区别：这里**有真算法**（AA 结算、推荐打分）、
**有外部集成**（天气/地图 API，能聊降级和缓存）、**有定时任务**（车票提醒，能聊幂等）。

## 二、给谁用、怎么用（跟着一趟出行的节奏）

| 阶段 | 用它做什么 |
|---|---|
| 出发前 | 建行程 → 邀请码拉朋友进来 → 看目的地天气 → 自动生成出行清单 → 分头收拾、谁收拾好谁勾掉 |
| 出发前（决策） | 按口味和天气推荐去哪吃、去哪玩（每条带推荐理由），一键跳地图 / 美团 |
| 路上 | 车票录入后定时提醒「还有 2 小时发车」（不重发、不遗漏） |
| 回来 | 把账记上 → 一键 AA 结算 → 照「谁该给谁转多少」直接转账 |

## 四、核心亮点（项目里最重要的东西）

**★★ ① AA 结算引擎 —— 全项目技术含量最高的一点**

- 金额全链路用整数「分」（`long`），不用 double：`0.1 + 0.2 = 0.30000000000000004`
  是浮点数的固有精度问题，记十几笔账后就会差几分钱
- N 人分摊用「整数分 + 余数按序分配」，保证**分摊总额与账单零误差**；
  成员先排序，保证**结果可复现**（同样的账单算两次结果一致）
- 算法抽成**零框架依赖的纯函数**（无 Spring 注解），可脱离容器秒级单测
- 诚实说：双指针贪心只是近似解，最少转账笔数（子集和）是 NP-hard，不保证最优

**★★ ② 天气 × 清单联动建议 —— 产品的灵魂功能**

- 天气**双数据源**（高德 + 和风）：接口抽象 + 防腐层统一数据形状 + 单源故障
  **自动降级**（一个挂了自动换另一个，全挂返回"暂不可用"而不是报错）
- **只缓存真实数据**：降级/演示数据不缓存，避免假数据污染后续请求
- 「什么天气带什么」做成**可配置规则**（存数据库）：加一条规则只插一行数据，
  **不改代码、不发版**；写入时严格校验（400），运行时脏规则只告警不拖垮接口

**★ ③ 地点推荐与出行跳转**

- 推荐是**可解释加权打分**（偏好 / 距离 / 口碑），每条结果都带推荐理由 ——
  用户相信的不是分数，是「为什么推这个」
- 地图深链适配过一个真实的坑：高德是「经度,纬度」、百度是「纬度,经度」，
  顺序相反；后端统一拼好，各端不用各踩一遍

**★ ④ 上线与安全底线**

- 已真实部署：prod 配置（MySQL + 表结构只校验不修改）+ 登录自启 + 一键重新部署
- 全链路**越权防护**：子资源查询强制带父级 ID，越权返回 404（不泄露资源是否存在）
- **幂等**：提醒任务一天扫 288 次，靠"标记位 + 数据库唯一约束"两道防线不重发
- 密钥只存在于环境变量文件（不进 Git），代码里只有占位符

## 五、快速开始

**方式 A · 直接看（已部署）**

服务已在服务器上运行，打开 `http://<服务器IP>:8080` 能看到**服务状态页**
（服务在线、接口一览、测试覆盖数字）。

**方式 B · 本机跑（Windows，双击即用）**

| 想干什么 | 双击什么 |
|---|---|
| 开发模式跑起来（H2 文件库，零依赖） | `启动后端.bat` |
| 用生产配置跑（真 MySQL，第一次先 `init` 建表） | `deploy\本地跑生产模式.bat` |
| 跑全部验收脚本（8 套 + 全量回归） | `运行验收.bat` |
| 改完代码一键重新部署（停旧进程→打包→启动→健康检查） | `deploy\重新部署.bat` |

> 密钥在 `deploy\local-env.bat`（从 `local-env.bat.example` 复制改值，已被 gitignore）。

**方式 C · 从源码构建**

```bash
# 需要 JDK 21 和 Maven；数据库默认用 H2，不用装 MySQL
mvn clean package
java -jar target/trip-companion-server-0.1.0.jar     # 默认 dev 配置
```

另外还有一个**可交互的网页演示壳**（独立的 `trip-companion-web` 项目）：
双击它的 `启动.bat` → `http://localhost:5173`，能点完整界面（演示数据模式）。

## 六、接口一览（分组）

| 组 | 代表接口 | 说明 |
|---|---|---|
| 健康检查 | `GET /api/health` | 服务状态 + 天气源配置情况 |

| 天气 | `GET /api/weather?city=…`、`GET /api/trips/{id}/weather` | 按城市 / 按行程 |

## 七、架构与关键设计

```
浏览器 / curl
     │
     ▼
Spring Boot 3.3（内置 Tomcat，单 jar 部署）
     ├── 统一响应 + 全局异常（400/404/405/415/500 语义分明）
     ├── 令牌鉴权拦截器（Authorization: Bearer）
     │
     ├── trip 行程与成员 ── 权限模型（创建者/成员，越权 404）
     ├── checklist 清单 ──┬─ 天气×清单规则引擎（规则存表，纯函数匹配）
     │                    └─ 建议/一键采纳（天然幂等）
     ├── expense 记账 + settle AA 结算（整数分，纯函数）
     ├── weather 天气（高德/和风 双源 + 降级 + 只缓存真实数据）
     ├── poi 推荐（可解释打分 + 地图深链）
     └── ticket 车票 + reminder 定时提醒（标记位 + 唯一约束两道防线）
     │
     ▼
MySQL 8（9 张表：user/token/trip/member/checklist_item/rule/expense/ticket/reminder）
外部依赖：高德（天气+POI）· 和风天气（备用源）· 美团/百度/高德地图（深链跳转）
```

几个值得知道的取舍（每句都能展开讲）：

- **不透明令牌 vs JWT**：令牌存数据库，能随时撤销（退出/被盗）；代价是每次多查一次库。
  多台服务器、不想查库时再换 JWT。
- **存 id 不用 `@ManyToOne`**：避免 N+1 查询和 `LazyInitializationException` 两个经典坑；
  多写几行查询，但 SQL 是什么一眼能看懂。
- **「行程不存在」和「你没权限」返回同一个 404**：返回 403 等于告诉对方"这个行程存在"，
  别人就能遍历 id 探测。代价是调试信息略少，值得。
- **`ddl-auto` 开发 `update`、生产 `validate`**：update 会自动改表结构，线上很危险
  （改个字段名可能把列删掉）；validate 只校验，不匹配就启动失败——失败能立刻发现。
- **开发/生产双 profile**：dev 用 H2（不用装数据库）、有 `/api/dev/*` 调试接口；
  prod 用 MySQL、调试接口 404、日志落文件。

## 十一、边界说明（它**不是**什么）

诚实地说清楚，避免误会：

- **不是小程序**：是网页演示壳 + Java 后端（小程序版已放弃）
- **不是分布式 / 微服务**：单体应用；没上 Docker/K8s；没做压测，不知道 QPS 上限
- **前端演示壳不连后端**：那个网页版是本地演示数据（localStorage），后端才是正经交付物
- **认证是自建令牌表**，不是 JWT；表结构变更还没接 Flyway（用 SQL/手工管理）
- **外部依赖需要 Key**：高德/和风的 Key 在环境变量里，仓库内不含真实密钥
